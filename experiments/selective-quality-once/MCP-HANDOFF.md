## Lifetime and one-shot boundaries

Use one process, with exec_command tty:true and write_stdin for replies. Actual tool probe confirmed this is supported; non-TTY exec closes stdin and safely stops. Do not restart the live process or copy prior responses into a new session. `handoff-started.json` is exclusive and fsynced; it is never deleted by the program. A new workspace gets a new in-memory session ID and claim nonce, and the fixed DB trial/attempt prevents a second fresh claim. Old response envelopes cannot match the new session/request; same-process duplicate or invalid envelopes permanently close the bridge. Raw response SHA256 detects accidental mutation, not forgery by a trusted operator. The operator must preserve actual MCP provenance.

Default mode is mock, and every mock request has project LOCAL_POSTGRES_ONLY_DO_NOT_SEND_TO_MCP. NEVER submit it to hosted MCP. Only explicit --execute-approved-trial emits the approved project. No real invocation occurred during development. Even mock SQL must only run in the isolated disposable PostgreSQL fixture.

The new handoff uses a fixed 180,000ms dispatch window (the old connectorOnce default remains 10,000ms). Start is after fixture/provider-input preparation. Four sequential pre-dispatch tool calls are required: reserve+claim, claim-XID proof, state inspection, final state inspection after durable marker. The observed single read was 7.831s (~31.3s for four if comparable; this is not a latency guarantee). 180s allows bounded operator/file round trips; no automatic reset or extension. Each outstanding handoff has a separate nonrenewing60s timeout. Slow calls can therefore stop the trial with its reservation retained; that is intentional. User/operator must not execute a request once the process has exited/timed out.

Both Date.now elapsed and monotonic performance.now elapsed must remain nonnegative and <=180s; a pause advancing either clock expires the run. Separate DB reads must have observed_at between claim.server_issued_at and +180s and the job must still be running/unexpired, attempt pending, owner active admin, identity/hash/nonce matching. The 24-hour job expiry is unrelated and is not an execution permit. Provider preparation happens before the window; no asynchronous image preparation occurs between final check and fetch. This is not atomic with an arbitrary concurrent administrative change after the last read.

## Preservation review: remaining conditions classified

1. Hosted total latency: runtime fail-closed condition, not an unimplemented timeout. One process is bounded by 180s before dispatch and60s for each pending response. Full live MCP trial latency has not been measured; a missed deadline stops and retains the reservation. No automatic extension or replacement trial is allowed.
2. Tool-response provenance: operational trust boundary, not cryptographic authentication. The full tool-return object can be captured directly by the supported tools orchestration, JSON-serialized without extracting/retyping its result rows, and transferred to the local evidence directory. Request metadata can then be copied programmatically (snippet below). Passing the resulting stdout string directly to write_stdin avoids manual field reconstruction. Binding/hash/parser reject accidental edits, but a privileged caller that fabricates both response and hash is outside this model. If raw capture cannot be preserved, stop rather than manually repair a result.

Programmatic envelope construction (local only; not executed by this document):
```js
import {readFileSync} from 'node:fs';
import {createHash} from 'node:crypto';
const request=JSON.parse(readFileSync(requestFile,'utf8'));
const response=JSON.parse(readFileSync(wholeToolResponseFile,'utf8'));
const keys=['mode','sessionId','requestId','sequence','project','owner','trial','attempt','sqlHash'];
const envelope=Object.fromEntries(keys.map(k=>[k,request[k]]));
envelope.response=response;
envelope.responseHash=createHash('sha256').update(JSON.stringify(response)).digest('hex');
process.stdout.write(JSON.stringify(envelope)+'\n');
```
requestFile is the existing immutable handoff-N-request.json, and wholeToolResponseFile holds the complete original official MCP return object, not a model-written summary. The supported orchestration can pass this output directly as write_stdin.chars on the same PTY session; no credential or provider image belongs in that envelope. Read the request file rather than a truncated terminal display. No new security/DB/network permission is implied.
