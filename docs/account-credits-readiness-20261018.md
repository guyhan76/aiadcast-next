# 내 이용권과 생성 준비 조회

기준: 사용자 전달 Live PR30 `26526baec74206cd51657a7f670fefa7c1f35226`. 후보 브랜치 `feat/account-credits-readiness-20261018`, Android demo 0.2.31 / versionCode 33. PR29 규격 복구는 포함하지 않는다.

- 헤더 내 이용권은 구매 화면 대신 `#credits`로 이동한다. 인증된 `GET /api/account/credits`가 현재 사용 가능·예약 이용권, 최근 구매/관리자 지급 각 30건을 반환한다. 요청의 userId로 다른 사용자를 조회할 수 없다. 결제 승인·지원 적용·생성 요청을 수행하지 않는다.
- 조회 중/완료 시각/실패/성공했지만 빈 내역을 구분한다. 실패와 미조회는 0으로 표시하지 않는다. 15초 타임아웃 후 재시도할 수 있다. 구매와 결제 복귀는 별도 버튼이다.
- 생성 상태 재조회는 중복 요청을 막고 진행 상태, 완료 시각, 변경 없음과 계속 차단된 이유를 표시한다. 회원 API 예산이 0이면 예산 미배정이며 추가 결제로 해결되지 않는다고 설명한다. 이용권·예산·규격 gate는 유지한다.
- 실제 보고된 이용권 34개를 과거 1개와 혼동하지 않는다. 기존 지원 정책은 available+reserved가 3 이상이면 추가 지급 0이다. 대체 PostgreSQL 테스트에서 34개 보존, 관리자 $4/회원 $1/전체 $5와 재적용 중복 지급 방지를 검증한다. 작업자가 운영 지원 조회/적용을 수행했다는 뜻은 아니다. 이후 운영자가 직접 적용한 화면을 부모가 확인했다: 회원 guyhan76@gmail.com, 전체 $5/관리자 $4/회원 $1, 이용권 34·예약 0·추가 지급 0, 중복 지급 없음. 적용 전 관리자 사용 $0.5996·보류 0. 이 전달 근거를 보존하며 추가 지원이나 배정을 실행하지 않는다. UI는 현재 응답에 따라 안내하며 회원 예산 0을 고정하지 않는다.

DB 스키마·환경변수·예산 정책·인증 권한 변경은 없다. 프런트/API를 함께 배포한 뒤 같은 서명의 APK로 업데이트한다. APK만 설치하고 구버전 서버에 연결하면 조회 실패 안내가 나온다. 기존 34개를 다시 지급하거나 결제하지 않는다.

배포는 운영자가 현재 Render 서비스 `srv-db65sol9fdbs73eu33i0`, 연결 브랜치, 환경, 승인 SHA와 CI 결과를 확인한 후 별도로 진행한다. `main`/PR5로 덮어쓰지 않는다. 이미 적용한 monthly_demo_support 저널을 보존해야 하므로 지원 정책 이전 구버전으로 단순 롤백하지 않는다. 추가 운영 예산 지원은 별도 조회 결과 검토와 승인이 필요하다. 본 작업에서 실제 결제·AI 생성·키 변경·운영 배포·지원 적용은 하지 않았다.
