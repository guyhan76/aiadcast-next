# Admin overview timeout: server-only candidate

Base: deployed e6e9d3299ff5d978d0c661ed0a457fab286551fd. The observed client error is its 15-second overview timeout, not evidence of a role denial. Production trace timing remains unavailable; this change removes a demonstrated expensive/side-effecting path, rather than claiming a proven original root cause.

The Supabase production overview now uses one repeatable-read, read-only transaction. It makes three data-query round trips (account snapshot, schema catalog, bounded UNION summary), six round trips including transaction controls. There is no member service initialization, schema migration, generation recovery, reservation expiry, provider call, asset download or write/advisory transaction lock. The HTTP authentication and admin role check remain unchanged. Other generation/admin operations retain their existing code paths; the local SQLite development fallback is unchanged.

Bounds: at most 200 members, 30 recent jobs per member and 60 returned jobs, 50 orders and 50 audit entries. More than 200 members returns an explicit 503 rather than silently truncating totals; pagination is not introduced because existing APK compatibility is preserved. Pool acquisition times out after two seconds; each data statement has a 2.5-second database timeout and a 750ms lock timeout. Network stalls can still outlast database timeouts; this is not a universal response-time guarantee.

Current stored reservations are displayed without reconciliation. Entirely absent member schemas use their recorded initial test-credit allocation (the same value initialization would grant) without creating a ledger; an extra ledgerInitialized=false flag identifies this case. A missing monthly budget row or v2 wallet row has the existing ledger's defined zero semantics. Partial schemas, missing initialized legacy wallets and failed queries fail the entire snapshot with 503, never substitute zero balances or incomplete totals. The existing APK retains any last successful data and shows its established refresh-error state.

Validation: 31 existing admin/cloud domain checks passed; six targeted mocked overview checks passed including 200 users, bounded query count, unauthorized, empty, partial/error, uninitialized and member-limit cases. One new real PostgreSQL-compatible PGlite integration check proves the HTTP overview neither expires a past-due ready job nor creates an unused member schema; jobs, wallets, credit events and budgets are byte-for-byte equivalent as returned SQL records before/after. Two desktop/mobile admin timeout/authorization UI checks passed. TypeScript/web build and generated cloud consistency checks passed. All providers/accounts/payments in tests are local fixtures.

No environment, role, API-key, plan or billing-policy changes are needed. No production overview endpoint or production database mutation was executed during diagnosis/testing.
