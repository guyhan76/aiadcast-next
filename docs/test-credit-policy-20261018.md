# 테스트 크레딧 정책 · 2026-10-18

이 변경은 승인된 테스트 상품과 테스트 원장의 구현이다. 실결제·실제 AI 호출·키 생성·환경변수 변경·운영 DB 변경·운영 배포는 실행하지 않는다. 관리자의 이용권 면제는 공급사 비용 무제한 승인이 아니다.

## 기존 이용권과 전환

- 기존 이용권 1개는 이전과 같이 1회 생성에 예약하고 사용 확정 때 차감한다. 기존 반려·실패·24시간 검토 만료의 복원 규칙을 유지한다.
- 사용 가능한 기존 이용권을 먼저 사용하고, 없으면 신규 크레딧 10개를 예약한다. 이미 예약된 기존 이용권은 다른 작업에서 재사용하지 않는다. 서로 단위를 변환·합산하지 않는다.
- 신규 작업은 `job_policies`에 `credit-v2` / `delivered-2026-10-18`을 기록한다. 기록이 없는 기존 작업은 `legacy-ticket` / `legacy-accept-v1`로 해석한다. 역할이 바뀌어도 작업 당시 정책을 유지한다.
- 기존 `wallets`, `purchases`, `jobs`, `credit_events`와 기존 금액·수량을 그대로 둔다. `credit_wallets`, `purchase_units`, `job_policies`, `defect_reports`만 추가한다. 기존 이벤트는 작업/구매 식별자로 단위를 결합해 조회한다.
- 이전 `trial/basic/bundle`로 새 주문은 만들지 않는다. 이미 저장된 주문은 주문 당시 가격·수량을 그대로 사용한다. SKU는 단위·정책 버전을 고정하는 식별자이며 기존 SKU의 의미를 재정의하지 않는다. 주문 요청 ID가 같은데 SKU가 다르면 거부한다.
- 신규 크레딧 요청에는 현재 단위·차감량·정책 버전의 명시적 `creditQuote`가 필요하다. 구버전 앱이 이를 보내지 않으면 공급사 호출 전에 거부한다. UI는 잔액·예약량과 10개 차감을 표시하고 확인을 받은 뒤 실행한다. 잔액이 변해 다른 단위가 필요해지면 자동 전환하지 않고 재확인을 요구한다.

## 차감·복구

신규 크레딧은 정상 이미지와 사용량/비용 기록을 저장하고 결과를 제공 가능한 상태로 만들 때 예약분을 한 번 차감한다. 사용 확정은 검수·적용 행위이며 두 번째 차감이 아니다. 정상 결과 미확인·검토 지연·취향에 따른 반려는 자동 환급하지 않는다. 제공된 결과는 검토 시한 때문에 삭제하거나 무료화하지 않는다. 이미지의 파일 유효성과 제공 성공을 자동 의미·물리 정확도 보증으로 설명하지 않는다.

결과 제공 전 시스템 실패·만료는 해당 단위의 예약분을 복원한다. 공급사 처리/비용이 불확실하면 고객 예약분은 복원하되 기존 공급사 비용 보류액과 자동 재실행 금지는 유지한다. 작업/구매/이벤트 식별자에 따른 중복 방지와 서버 트랜잭션을 사용한다. 성공 응답 유실은 기존 작업/주문 조회로 복구하며 새 생성이나 새 결제를 강제하지 않는다. 일부 작업만 성공한 경우 그 작업만 차감한다.

## 확인된 결함 처리

회원은 결과의 오류 설명을 `POST /api/generations/:jobId/report`로 접수한다. 작업 소유권을 확인하며 동일 작업의 중복 신고는 기존 신고를 반환한다. 신고만으로 잔액은 바뀌지 않는다. 관리자 화면에서 회원을 선택하고 **생성 결과 오류 신고 검토**를 펼쳐 조회한다.

관리자는 입력·결과를 실제로 비교한 근거를 기록해야 한다. 신고가 있는 작업만 관리자 전용 `GET /api/admin/defect-evidence?userId=...&jobId=...`에서 당시 입력·원본 사진·생성 결과를 읽어 화면에서 비교한다. 이 조회는 새 공급사 호출을 만들지 않는다. `GET /api/admin/defect-reports?userId=...`로 조회하고 `POST /api/admin/defect-review`에 `userId/jobId/decision/resolution`을 보낸다. `confirmed`는 해당 작업의 차감량을 같은 단위로 한 번 복원하고 `declined`는 유지한다. 서버 인증 역할을 확인하며 회원이 관리자 필드를 보낸 것으로 권한을 얻지 못한다. 검토자·사유·시간·결정과 원장 이벤트를 같은 트랜잭션으로 기록한다. 동일 결정 재전송은 중복 복원하지 않고 충돌한 결정 변경은 거부한다. 공급사 비용은 복원하지 않는다. 복원 후 고객이 다시 생성할 때는 일반 차감 규칙을 적용하므로 확인된 결함 한 건의 대체 생성분을 보전한다. 자동 품질 판정이나 무제한 무료 재시도를 구현한 것은 아니다.

서버 없는 체험은 기기 내 모의 잔액·차감과 신고 접수 표시만 제공한다. 실제 관리자 처리·공급사 결제의 증거가 아니다.

## 배포·되돌리기

대상 브랜치는 `feat/versioned-test-credits-20261018`이며 PR34의 `c4a324a9826e7d6d99c31da6f60fcb487c2b9728` 위에 쌓는다. main이나 과거 PR5를 배포 대상으로 삼지 않는다. 최종 커밋과 원격 CI는 해당 draft PR 및 작업 완료 기록에서 확인한다.

운영 배포 전 담당자가 Render 서비스, 연결 저장소·브랜치, 현재 운영 SHA, 환경, 인증 설정, DB 백업/복원 방법을 확인해야 한다. 이 작업은 그 설정을 변경하거나 배포하지 않는다. 추가 테이블은 로컬 SQLite와 로컬 PGlite PostgreSQL에서 검증한다. 실제 운영에서는 앱 초기화 시 기존 스키마에 추가 생성하므로 사전에 검토·승인한 유지보수 절차가 필요하다. 기존 DB 접근 권한, RLS 차단 및 공급사 예산은 확대하지 않는다.

신규 크레딧 구매·작업이 생기기 전이라면 기존 데이터와 추가된 빈 테이블을 보존한 채 이전 앱을 복구할 수 있다. **신규 작업이 생긴 뒤 구버전 서버로 단순 롤백하면 안 된다.** 구버전은 신규 작업의 10크레딧을 기존 이용권으로 오인할 수 있다. 생성·주문 접수를 중지한 뒤 이 버전의 원장 처리기를 유지하는 전진 수정이 우선이다. 구버전 복구가 꼭 필요하면 백업·진행 작업·구매·잔액을 함께 대조하는 별도 마이그레이션/복원 계획을 먼저 승인받아야 한다. 앱만 구버전으로 바꾸면 신규 잔액을 사용하지 못하므로 지원 버전 안내가 필요하다. 이미 차감한 작업을 삭제하거나 잔액을 임의 환산해 되돌리지 않는다.

실제 평균 생성 원가·가격 수익성·오류율·고객 인증·실결제·Android 실기기/스토어 검증은 별도다. 테스트 통과와 APK 제작을 운영 배포나 수익성 검증으로 보고하지 않는다.
