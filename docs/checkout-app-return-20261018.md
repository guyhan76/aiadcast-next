# 테스트 결제 후 시연 앱 복귀

기준은 사용자 확인 Live `d86a8c33d36a0438fa885bdd509aa4ef85aee12c` (Render `dep-dba8rhrncjis73clbdig`, 2026-10-18 09:14:33 UTC 완료)다. 별도 `feat/checkout-app-return-20261018` 브랜치이며 PR29 박스 규격 복구는 포함하지 않는다. 원격 main으로 이전 기능을 덮어쓰지 않는다.

## 고객 흐름

- 외부 브라우저는 기존 주문 전용 ticket으로 승인 후 `POST /api/checkout/receipt`를 조회한다. 로그인 세션을 브라우저에 복제하지 않는다.
- `paid`뿐 아니라 주문 ID에 대응하는 구매 원장의 사용자·지급 수량을 검증한다. 3개 상품이면 정확히 +3 구매 기록과 현재 이용 가능 잔액을 표시한다. 잔액은 이전 잔액·사용량에 따라 3과 다를 수 있다.
- `광고 만들기 계속` 버튼은 고정 `aiadcast-demo://checkout/return`을 연다. 로그인 토큰·paymentKey·ticket·주문 ID·임의 복귀 URL을 넣지 않는다. 이 주소는 검증된 고정 입력만 받는 demo 전용 custom scheme이며 도메인 소유권 인증 Android App Link라고 주장하지 않는다. 다른 앱이 같은 scheme을 등록해도 이 신호에는 인증이나 지급 권한이 없다.
- 새 APK는 demo manifest에서만 해당 intent를 받고, package/action/전체 URI를 검사한다. warm return은 현재 WebView를 재로드하지 않고 고정 이벤트를 보낸다. cold return은 로컬 복귀 화면에서 로그인 필요 여부부터 확인한다.
- 앱은 로컬에 저장한 origin·userId·orderId·입력 경로와 현재 계정을 대조하고 인증된 주문 API를 재확인한다. 성공하면 별도 생성 요청 없이 원래 초안으로 바로 돌아가 지급 안내를 표시한다. 사진·설명·규격은 기존 IndexedDB 계정별 작업을 사용한다. 입력이 없으면 새 입력 화면이다.
- 복귀 정보와 공개 ticket 기반 승인/영수증 확인은 24시간 제한. 이후에는 앱의 본인 인증 주문 조회로만 복구한다. 취소·미확인·다른 계정은 자동 이동하지 않는다. 로그인 만료 시 같은 계정으로 다시 로그인한다. 외부 URI의 다른 경로/쿼리/fragment/host는 모두 무시한다.
- 앱 미설치·구버전·브라우저 scheme 차단은 수동 앱 실행 안내와 웹 이용권 확인 링크를 제공한다. 구버전 APK에서 이미 완료한 결제는 새 앱의 `내 이용권 → 결제 후 작업 이어가기 → 이전 결제 내역 확인`으로 본인 주문을 선택해 재검증한다. 새 결제는 필요 없다. 사진이 다른 기기/브라우저로 이동하지는 않는다.

## 과금과 실패 복구

구매 원장의 기존 고유 purchase ID를 유지해 중복 승인/새로고침/재시작이 추가 지급하지 않는다. 지급 기록이 없으면 paid 문자열만으로 성공을 표시하지 않는다. 만료/취소 주문에 새 승인 POST를 하지 않으며 이미 승인된 결과 조회·원장 복구는 유지한다. receipt 조회 자체는 provider 호출과 지급을 하지 않는다. 기존 인증 주문 status는 미완료 주문의 승인 결과를 조회해 기존 idempotent 지급을 복구할 수 있다.

새 DB 테이블·예산 증액·회원 지원·키 설정은 없다. 테스트 이용권 지급과 회원 API 예산 $0 또는 규격 gate 해소는 별개다. 실제 추가 테스트 결제/실결제/이미지 생성은 실행하지 않았다.

## 전달과 배포 순서

APK `com.selluplabs.aiadcast.next.demo`, versionCode32 / 0.2.30-demo. 기존 승인된 demo 서명을 재사용한다. APK에는 비밀키가 없다. 업데이트 설치하며 기존 앱을 삭제하지 않는다. 실제 기기의 Samsung Internet → Android intent → 초안 복구는 설치 후 별도 확인해야 한다. 자동 브라우저 검사는 native 이벤트 모의, Android unit 검사는 URI 정책이며 실기기 증거와 구분한다.

이번 작업은 서버/웹 운영 배포를 하지 않는다. 승인 후 실제 서비스·브랜치·SHA·환경을 확인하고 이 브랜치 서버/웹과 APK를 함께 적용해야 한다. 구 서버는 receipt 증거를 제공하지 않으므로 새 복귀 화면은 확인 실패로 안전하게 멈춘다. 구 APK는 새 scheme을 처리하지 못하므로 수동 안내로 이어진다. 새 APK만으로 운영 외부 결제 페이지가 바뀌지 않는다.

PR29와 통합할 경우 별도 통합 브랜치에서 두 변경을 합치고 특히 StudioApp, generation-service, cloud 파생 코드, native 버전을 다시 검증해야 한다. PR29를 이 브랜치에 포함했다고 간주하거나 두 후보 중 하나를 다른 하나 위에 무검증 배포하지 않는다. 기존 PR27의 구매/지원 원장 및 spent/held 보존 롤백 조건은 유지한다.
